One cache per node; each tree describes local data

Requester and responder name the roles in an exchange. They are not different kinds of DigestTree. A node can use the same maintained cache when fetching from another node or serving its own local data.

The node asks whether an existing TreeSpec can serve the Selection. The tree must contain every required member, and its key layout must express the requested range and any ordering needed by LIMIT. The node also checks credentials and policy-filtered access. Before each offer, the entry checks current permissions and catches up through a finite committed revision.

One resident tree can serve several query scopes. A tree covering every match for project = 'acme' AND foo > 7, keyed by project and foo, also serves foo > 10 within that project. It cannot serve foo > 3. Compatible ORDER BY and LIMIT changes select a view from that complete tree; they do not change its TreeSpec or truncate its membership. Frozen comparisons retain their captured contents.

A cold limited query keeps a bounded result. If no complete tree can serve ORDER BY foo LIMIT 10, the node reads and retains only that result. The cache records limited coverage separately from TreeSpec. This entry can serve the same Selection with compatible access and key layout; it cannot stand in for an unlimited or differently limited query. When a change can affect its result, a validated bounded read finds replacements. Complete and limited entries use the same cache and RAII ownership.

Each resident entry consumes committed entity changes even when idle. Every active Fetch and subscription holds an RAII lease. Dropping the last lease makes the tree eligible for eviction in least-recently-used order. The idle retention allowance is 32 entries and 128 MiB of accounted row and tree memory. It does not impose a new limit of 32 active queries; active streams keep their separate limits. Eviction does not delete stored entities or invalidate snapshots already held by an active comparison. A live query keeps its lease between comparison rounds and through a disconnected peer. Replacing that query generation or dropping the query releases its lease. Small inventories covering the captured tree can be produced without constructing digest nodes; selecting a narrower view from a complete tree may construct its digest nodes to resolve the bounds.

This guide describes the digest-tree feature branch. It is a review preview, not documentation of a released version.

What the tree-related types mean

TypeMeaning
TreeSpecThe tree’s membership predicate and canonical key layout.
TreeSpanAn exact interval of full tree addresses. The endpoints include the key bytes; no external prefix is prepended to interpret them.
TreeSpanDigestA span, its aggregate digest and count, plus a containing subtree prefix used for refinement.
EntityHeadAn entity ID and its full causal clock.
KeyedEntityHeadAn EntityHead plus this tree’s property-key bytes. The ID distinguishes entities with equal keys.
TreeSpanInventoryA span and every matching entity head within it. Empty heads explicitly mean no matches within those bounds.
SpanContentEither Heads(TreeSpanInventory) or Digest(TreeSpanDigest).
KnownStateThe requester’s TreeSpec and disjoint spans describing its captured query result.

KnownState is required in Fetch and SubscribeQuery; RefreshState supplies a new one. An empty inventory says “no matches here.” An empty spans list or omitted range says “unknown.” Neither says that the requester has no entity state cached outside this query.

The current offer producer uses one request-sized inventory when small enough, otherwise a bounded frontier of span digests. The protocol accepts disjoint mixtures too. Different follow-up page limits do not require splitting and gluing back together an initial inventory.

Inventory encoding and crate ownership

Inventories use PackedHeads. Sorted key prefixes can be encoded once and reused by suffixes in a flat buffer; plain encoding is used when smaller. Borrowed cursors read the packed heads. The walkthrough expands them for readability.

TreeSpec, TreeSpan and TreeSpanDigest belong to digest-tree. Entity clocks, inventories and KnownState belong to proto because they describe peer knowledge with actual clocks. The standalone tree works with head hashes and does not manage network exchanges.

Requests each have their own request ID. Pushed frames retain the original Fetch/SubscribeQuery request ID, even after refresh, and also carry an update ID and a stream frame sequence. A control response and a separately pushed frame can arrive in either order.

Questions, answers and failure paths

StateItem::Digest asks for the requester’s digest over the same bounds. StateItem::NeedHeads asks for exact keys, IDs and clocks. Answers travel in ContinueState.answers. Neither the routing UpdateAck nor the control Success is that comparison answer.

Retryable initial capture can return StateCaptureBusy. ContinueState and FinishStateRound can return StateStreamUnavailable; requests can also fail with Error. Later frames can report RestartRequired, SourceUnavailable, or RepairUnavailable. Required uncovered history is never silently treated as complete.

Four different claims

ClaimWhat it establishes
progress: CompleteThe responder finished enumeration for one captured round. Required connecting history may still be missing locally.
processed_throughThe receiver processed a contiguous frame prefix; those sender buffers can be released. Entity application need not be finished.
applied_throughAll live publications through a source revision have actual target coverage and have committed publicly. Their retained live repair targets can be released.
FinishStateRound: AppliedThe finite round’s targets are covered and its result is installed. Its snapshot can be released. Readiness does not wait for the Success reply.

For a live query, the finite round includes publications through its captured revision. Later writes do not keep moving that goal. Their application and membership obligations remain tracked independently.

Live delivery can happen during comparison. Committed later membership decisions survive installation of an older baseline. A logical live publication can span frames; complete: true marks its final fragment, and public membership plus causing events wait for actual target coverage.

A round can be cancelled without claiming coverage. FinishStateRound { outcome: Cancelled } preserves the standing stream. AbandonStateStream ends the stream and any active round. A Fetch stream retires when its sole round finishes.

Budgets are implementation policy

The responder chooses how much data and work to do per pass; requests do not select a ResponseBudget. A frame can contain several tree-related items, and the protocol does not require one tree tier or one page per request.

  • Initial offer: up to 2,048 heads when the request’s packed and expanded-size checks allow; otherwise a digest frontier bounded by 16 KiB, 128 spans and 32 refinements.
  • Follow-up head inventories: at most 128 heads per page, possibly fewer because of byte/work limits.
  • Responder production pass: 64 KiB item/work budget, up to 128 work steps and 32 tree/history operations; envelope allowance adds 4 KiB to the hard frame cap.
  • Ordinary send window: 4 MiB, with separate frame-count and reserved-control capacity limits.

These are current branch policies, not performance guarantees. Cold, large transfers need many frames but no information-dependent question turn if the requester has supplied exact empty coverage. They can still wait for credit or repair history.
