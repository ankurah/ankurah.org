One cache per node; each tree describes local data

Requester and responder name the roles in an exchange. They are not different kinds of DigestTree. A node can use the same maintained cache when fetching from another node or serving its own local data.

The node asks whether an existing TreeSpec can serve the Selection. The tree must contain every required member, and its key layout must express the requested range and any ordering needed by LIMIT. Two readers share a tree only when their effective access is equal: the policy restricts their queries the same way and lets them retrieve the same entities, and each holds a fresh policy proof that it may read every entity state. The node checks this when a reader takes a lease and on every use; where per-entity read checks could differ between readers, each gets its own tree. Before each offer, the entry checks current permissions and catches up through a finite committed revision.

One resident tree can serve several query scopes. A tree covering every match for project = 'acme' AND foo > 7, keyed by project and foo, also serves foo > 10 within that project. It cannot serve foo > 3. Compatible ORDER BY and LIMIT changes select a view from that complete tree; they do not change its TreeSpec or truncate its membership. If the keys cannot determine the requested limited ordering, the query uses its own bounded tree. This also applies to descending limited views when the predicate may admit missing sort values. The bounded tree uses storage to refill its membership when changes cross the limit. Comparison snapshots retain only metadata: keys, IDs, Clocks and digests. Entity payloads remain in the resident entity or storage engine.

A cold limited query keeps a bounded result. If no complete tree can serve ORDER BY foo LIMIT 10, the node reads and retains only that result. The cache records limited coverage separately from TreeSpec. This entry can serve the same Selection with compatible access and key layout; it cannot stand in for an unlimited or differently limited query. When a change can affect its result, a validated bounded read finds replacements. Complete and limited entries use the same cache and RAII ownership.

Each resident entry owns a reactor subscription and consumes committed entity changes even when idle. The subscription is registered before the admission scan; changes crossing the scan are applied before the tree can be used. Its bounded update queue contains key/head metadata and event IDs, never entity payloads or strong entity handles. A tree that cannot keep up fails explicitly and must be reacquired. Every active Fetch and subscription holds an RAII lease. Dropping the last lease makes the tree eligible for eviction in least-recently-used order. The idle retention allowance is 32 entries and 128 MiB of accounted metadata and tree memory. It does not impose a new limit of 32 active queries; active streams keep their separate limits. Eviction does not delete stored entities or invalidate snapshots already held by an active comparison. A live query keeps its lease between comparison rounds and through a disconnected peer. Replacing that query generation or dropping the query releases its lease. Small inventories read the snapshot’s ordered membership directly, including when selecting a narrow view from a larger tree. A resident tree builds its digest nodes the first time a comparison reads a digest and maintains them on every commit after that; while its comparisons exchange only small inventories, it builds none. A comparison reads digests from its own snapshot, so they agree with the entries that snapshot froze; a partial view never replaces the resident’s complete digest.

This guide describes the digest-tree feature branch. It is a review preview, not documentation of a released version.

What the tree-related types mean

TypeMeaning
TreeSpecThe tree’s membership predicate and canonical key layout.
TreeSpanAn exact interval of full tree addresses. The endpoints include the key bytes; no external prefix is prepended to interpret them.
TreeSpanDigestA span, its aggregate digest and count, plus a containing subtree prefix used for refinement.
EntityHeadAn entity ID and its full causal clock.
KeyedEntityHeadAn EntityHead plus this tree’s property-key bytes. The ID distinguishes entities with equal keys.
TreeSpanInventoryA span and every matching entity head within it. Empty heads explicitly mean no matches within those bounds.
SpanContentEither Heads(TreeSpanInventory) or Digest(TreeSpanDigest).
KnownStateThe requester’s TreeSpec and disjoint spans describing a snapshot of its query result.

KnownState is required in Fetch and SubscribeQuery; RefreshState supplies a new one. An empty inventory says “no matches here.” An empty spans list or omitted range says “unknown.” Neither says that the requester has no entity state cached outside this query.

The current offer producer uses one request-sized inventory when small enough, otherwise a bounded frontier of span digests. The protocol accepts disjoint mixtures too. Different follow-up page limits do not require splitting and gluing back together an initial inventory.

Inventory encoding and crate ownership

Inventories use PackedHeads. Sorted key prefixes can be encoded once and reused by suffixes in a flat buffer; plain encoding is used when smaller. Borrowed cursors read the packed heads. The walkthrough expands them for readability.

TreeSpec, TreeSpan and TreeSpanDigest belong to digest-tree. Entity clocks, inventories and KnownState belong to proto because they describe peer knowledge with actual clocks. The standalone tree works with head hashes and does not manage network exchanges.

Each request has its own request ID and gets exactly one response; a one-way message gets none. Pushed frames carry the original Fetch/SubscribeQuery request ID, even after refresh, and a stream frame sequence. A control response and a separately pushed frame can arrive in either order.

Questions, answers and failure paths

StateItem::Digest asks for the requester’s digest over the same bounds. StateItem::NeedHeads asks for exact keys, IDs and clocks. Answers travel in StateFeedback.answers, named by what they answer: Round { round, answers } answers one round’s questions and asks to repair its targets, and LiveRepair { requests } asks for connecting history toward live-publication targets. That history arrives in LiveRepair frames, which carry only repair items and change no membership. The control Success is not that comparison answer.

An initial Fetch or SubscribeQuery returns StateSnapshotBusy when the responder cannot take a stable snapshot while its source keeps changing; no stream is created. StateFeedback and FinishStateRound can return StateStreamUnavailable once their stream has expired or ended; requests can also fail with Error. Later frames can report RestartRequired or SourceUnavailable, and a repair can be RepairItem::Unavailable. After StateSnapshotBusy, StateStreamUnavailable or RestartRequired, the requester starts over with a new Fetch or SubscribeQuery; every retry is a new request. A failed stream closes only itself; the connection and its other streams continue. Required uncovered history is never silently treated as complete.

Membership as of the tree snapshot, current entity data

StateItem::Heads says which entities were in a span of the responder’s tree snapshot and at which Clocks. StateItem::Repair carries independently validated entity data. Before sending a payload, the responder reads its current resident entity or storage state and checks access again. It does not keep a second entity-state cache inside the tree.

If membership names Clock A but the entity has advanced to Clock B, the responder can send head A from its tree snapshot and current payload B. The receiver must incorporate both required targets; payload B cannot rewrite the membership recorded at A. Connecting events are requested if a snapshot alone cannot establish coverage. Live publications carry their causing events even if a current snapshot already applied those events’ state.

Four different claims

ClaimWhat it establishes
progress: CompleteThe responder finished enumeration for one round. Required connecting history may still be missing locally.
processed_throughThe receiver processed a contiguous frame prefix; those sender buffers can be released. Entity application need not be finished.
applied_throughAll live publications through a source revision have actual target coverage and have committed publicly. Their retained live repair targets can be released.
FinishStateRound: AppliedThe finite round’s targets are covered and its result is installed. Its snapshot can be released. Readiness does not wait for the Success reply.

For a live query, the finite round includes publications through the revision its snapshot reflects. Later writes do not keep moving that goal. Their application and membership obligations remain tracked independently.

Live delivery can happen during comparison. Committed later membership decisions survive installation of an older baseline. A logical live publication can span frames; complete: true marks its final fragment, and public membership plus causing events wait for actual target coverage.

A round can be cancelled without claiming coverage. FinishStateRound { outcome: Cancelled } preserves the standing stream. AbandonStateStream ends the stream and any active round. A Fetch stream retires when its sole round finishes.

Both peers enforce the protocol’s limits

The protocol fixes the limits below, and its limits module lists the rest. Each peer sizes what it sends to fit them and refuses whatever it receives that exceeds them, so a peer that changed one alone would have its messages refused. Byte limits count a message’s work: its encoded bytes plus the bytes its inventories saved by sharing key prefixes. Within these limits the responder chooses how much data and work to do per pass; requests do not choose its budget. A frame can contain several tree-related items, and the protocol does not require one tree tier or one page per request.

  • Initial offer: at most 2,048 heads, 128 spans and 256 KiB of work. The requester sends one inventory when it fits; otherwise it offers a frontier of span digests, which by its own choice stays within 16 KiB and 32 refinements.
  • Follow-up head inventories: at most 128 heads and 64 KiB of work per page.
  • Frames: at most 128 items and 64 KiB of item work, and 68 KiB in all. By its own choice, the responder also spends at most 128 work steps and 32 tree reads or history walks on one frame.
  • Send window: 4 MiB and 128 frames beyond those the requester has processed, plus reserved room for repairs and a stream’s final frame.

Either peer can change its own choices without breaking the other. None of these numbers is a performance guarantee. Cold, large transfers need many frames but no information-dependent question turn if the requester has supplied exact empty coverage. They can still wait for credit or repair history.
